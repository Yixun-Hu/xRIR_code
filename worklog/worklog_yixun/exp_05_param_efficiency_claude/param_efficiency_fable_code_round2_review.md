3. **should-fix — policy** — `tools/exp05_gates.py:64-99` (`set_budget`, the `min` at :91; "a re-probe cannot raise a spent arm's ceiling"). What the code does: once any `full` hours are booked on an arm, `ceiling = min(1.5 × T_run(new receipt), ledger ceiling)` for ever; the only escape is a hand edit of `cumulative_hours.json` (`hours_record` validates only `total_hours`/`attempts`), i.e. the plan's "renewed authorisation" has no code path. Reproduced: arm with receipt R1 (T_run 20 h → ceiling 30 h) aborts slow after 2.5 h; the plan-mandated re-probe R2 measures 27.6 h (clean, ≤ 60 h) → `2.5 + 27.6 = 30.1 > min(41.4, 30)` → refused; at 26 h it launches. So a relaunch is blocked exactly when the honest re-measurement exceeds ≈ 1.5 × the first projection minus what was spent (a ≥ 40–50 % slowdown between two clean probes, or a genuinely slower re-designed L). Judgement: the rule is *safe* (it only refuses, never over-spends) and reasonable as anti-probe-shopping, and it matches one reading of §3 ("1.5 × the probe projection … over all attempts"); it is stricter than the other reading (the receipt that certifies *this* launch sets the ceiling) and it can dead-lock an arm in precisely the case §3 says needs a human decision — without giving that decision a recorded form. Minimal policy (keep fail-closed, make the authorisation explicit and recorded): add `full … --renew-ceiling-hours H` which is refused unless `used + projection > min-ceiling`, requires `H ≥ used + projection`, `H ≤ 1.5 × T_run(new receipt)`, and appends `{renewed_at, from, to, receipt_sha256, argv}` to `cumulative_hours.json['ceiling_renewals']` and prints it; `_params_set_up.md` records every renewal. Alternative (simpler, less conservative): drop the `min` and record `ceiling_history` — I prefer the explicit flag. Not blocking: the first launch of every arm is unaffected.
