**1. `tools/paired_compare.py:307-309` — the `launcher` approved pin is checked against the *evaluation-launcher* (writer) closure, so `launcher` and `writer` are forced equal.**
`for approved, recorded in (('evaluator', 'entrypoint'), ('writer', 'writer'), ('launcher', 'writer'))` compares `profile['approved_closures']['launcher']` with `closures['writer']['sha256']` (= the `tools.exp04_eval_launch` closure). Plan §5 lists "evaluator, manifest-writer, launcher and producer" without saying whether "launcher" means the *training* launcher (`tools/exp04_launcher.py`) or the evaluation launcher. If the A9 JSON pins `launcher` to the training launcher's closure, every confirmatory analysis is refused at admission ("launcher approved closure"); if it pins it to the eval launcher, the key is redundant with `writer`. *Why it matters:* it must be settled in the A9 commit, before any real analysis. *Fix:* in the A9 schema, either drop `launcher` from the keys `paired_compare` validates (the training launcher's identity reaches the analysis only through the checkpoint sha256 and, once the 3b-fix lands, the train completion bound as a `mutable_inputs` entry), or define `launcher` as `tools.exp04_launcher`'s closure and *not* compare it in `_admit_run`. Add a docstring line stating the mapping.

**2. `tools/paired_compare.py:107-111, 447-451` — exclusion counts are keyed `"a"`/`"b"`, seed means are keyed by role.**
`cell_mask` returns `counts["a"]`, `counts["b"]`, `counts["joint"]`; `_analyze_cell` puts that dict into the cell as `exclusions` unchanged, while the neighbouring `seed_means` is keyed `"aug"`/`"control"` (verified: `exclusions keys: ['a','b','joint'] | seed_means keys: ['aug','control']`). Plan §3 asks for exclusions "reported per arm and seed"; the canonical JSON is the only source for `_results.md` and the results page, so the reader must know that `"a"` is the first profile arm. *Fix (3 lines):* in `_analyze_cell` remap `exclusions = {profile['arms'][i]['role'] if key in ('a','b') else key: value ...}` (H1/H2: a→aug, b→control; TOST: a→aug). Also cast the per-seed keys to `str` explicitly rather than relying on `json.dumps` to stringify ints, so the in-memory result and the JSON agree.

**3. `tools/paired_compare.py:266, 311, 375-406` — `_admit_run` cannot be reused for `TABLE_V1` as-is (round 5 fitness).**
It reads `profile['num_shot']` as an int (`profile['seeds'][shot]`), and `admit_runs` zips `profile['arms']` with exactly two run lists. `TABLE_V1` has `num_shot == (1, 8)` and three arms with 30 runs grouped by (role, K). The round-5 prompt tells the Coder to *import* these helpers. *Fix:* give `_admit_run` an explicit `num_shot` parameter (default `profile['num_shot']`), rename it `admit_run` (public), and let `admit_runs` accept a list of `(arm, num_shot, directories)` groups; `results_table.py` can then map each run's `checkpoint_sha256`/`manifest_seed`/`num_shot` to a `(role, K)` group and call the same helper. Everything else in `_admit_run` (grids via `run_grids[role]`, seeds via `seeds[shot]`, dataset identity, closures, reconciliation) is already K-agnostic.

**4. `tools/paired_compare.py:313-318` — the producer does not yet require the `confirmatory` flag the concurrent 3b-fix (cycle 4) adds to the eval manifest/completion.**
Per the Planner's round-3a close-out decision, the eval launcher will carry `confirmatory: bool` (true iff `max_samples == 0`, all queries evaluated, `--allow-dirty` unused) and `allow_dirty_used: bool`, and `mutable_inputs` names become fixed identifiers. `_admit_run` currently enforces `max_samples == 0`, `n_samples == split_count == 6337`, which is equivalent today but not bound to the flag. *Fix (follow-up, after the 3b-fix lands — cannot be done now):* add `'confirmatory': True` to `expected` and record `allow_dirty_used` in the result's `inputs`/sidecar; refuse unknown `mutable_inputs` names.
