## Findings

Severity legend: blocker / should-fix / nit.

1. **blocker** — `tools/exp04_launcher.py:302-336` (`run_child`) and `:356-408` (`execute_attempt`), `:444-522` (`main`). What: the abort-or-certify guarantee does not survive a signal. Only `KeyboardInterrupt` (SIGINT) reaches the `finally`/`except BaseException` path; SIGTERM and SIGHUP terminate the launcher with Python's default disposition, so the attempt directory is **not** renamed, no hours are accounted, `completion.json` is never written, and the trainer child — started with `start_new_session=True` — keeps running orphaned with no guard. Reproduced with a stub child sleeping inside step one: SIGTERM → launcher exit −15, root unchanged (`attempt_t` still there), stub child still alive; SIGHUP → identical; SIGINT → `attempt_t_ABORTED_child_failed`, child gone, hours accounted (Verified 6). Why it matters: the confirmatory run is a single 30 h attempt under a 43 h cumulative ceiling (one retry at most); a `kill <launcher>` or a hangup without `nohup` leaves a run that can neither be promoted nor aborted — and there is no `finalize` mode to recover it (finding 3). Minimal fix: at the top of `execute_attempt` (or in `main` before the lock) install handlers for `SIGTERM` and `SIGHUP` that raise (e.g. a `LauncherTerminated(BaseException)` subclass) so `run_child`'s `finally` kills the process group and `execute_attempt` renames/accounts, restoring the previous handlers afterwards; test: spawn the launcher (or `execute_attempt` in a subprocess) with a sleeping stub, send SIGTERM, assert `_ABORTED_*` exists, `cumulative_hours.json` has the row and the stub pid is gone. Document `nohup`/`setsid` plus a launcher log redirect in the launch command (finding 6).

## The 23 % probe overhead — attribution

The recorded probe (`_probe_20260912Tround3b_probe.json`) ran on GPU 1 shared with the FLAC job at 100 % utilisation: yaw-off 2.834 s/iter, yaw-on 3.487 s/iter, both arms ≈ 2× exp_01's dedicated-GPU 1.4 s/iter, peak memory identical (30.66 GiB). Measured on the same contended GPU 1 with CUDA events on a real-shaped batch (`[32,3,256,512]` float32 depth, `[32,3]` source, `[32,8,3]` references, 200 reps, first 20 discarded): `apply_yaw_aug` alone **median 1.066 ms, min 1.055 ms, max 1.11 ms**; the whole augmentation branch as executed by `compute_loss` (`offsets_for` on the CPU generator + `ks.to(device)` + `apply_yaw_aug`) **3.57 ms median / 3.41 ms min** of GPU time, **9.1 ms median / 5.8 ms min** wall (host-side draw and the pageable copy). Upper bound on a dedicated GPU: ≈ 10 ms per micro-batch ≈ **0.7 % of 1.4 s** (the rotation kernels themselves 0.08 %). The kernels are one gather over 50 MB plus a few elementwise passes; no allocation growth (peak memory equal). The 23 % therefore cannot be attributed to the augmentation path; it is co-tenant scheduling noise on 50-sample means taken minutes apart (the "on" arm ran second, under whatever the FLAC job was doing then). **The ≤ 5 % gate cannot be decided from this probe** — agreed with the Planner: it must be re-run on a clean GPU (the launcher's own `PROBE_NOT_CLEAN=true` and exit 1 say the same), preferably with finding 9's per-iteration record. Expectation for that re-run: overhead well under 2 %.
