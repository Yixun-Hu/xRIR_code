2. **should-fix** — `tools/exp04_eval_launch.py:34` (`_run_child`, console mirror). What: `tee /dev/stderr` *re-opens* the launcher's stderr target. When the launcher is started with `2> file` / `> file 2>&1` (no `O_APPEND`), tee's writes begin at offset 0 and overwrite the launcher's own earlier lines. Reproduced twice: my parity driver log lost the `WARNING: dirty_outside_worklog` line (the manifest proves the warning path ran: `dirty_outside_worklog: true`, `allow_dirty: false`) and its head is the child's first line; a 3-line test (`print; tee /dev/stderr; print` under `> f 2>&1`) leaves `CHILD-OUTPUT … LAUNCHER LINE 2` with line 1 destroyed. The canonical teed `log_path` is unaffected (it is the `stdout=log` side and its digest re-hashes). Why: the launcher's own gate output (dirty warning, abort reason) is what the Planner reads when a run is redirected to a file, and the SOP's launch logs are made that way. Fix: mirror the training launcher — `subprocess.Popen(["tee", "-a", str(log_path)], stdin=child.stdout, stdout=2)` while keeping the exclusive `open("xb")` for creation, or `stdout=sys.stderr.fileno()`; test with stderr redirected to a temporary file and assert the launcher's pre-spawn line survives.

If `_run_child`'s `open("xb")` raises `FileExistsError` because a file with that name already exists (same label and microsecond stamp), the launcher renames **someone else's** file to `<stem>_ABORTED_child_failed.log` (probed with a patched timestamp: the pre-existing "someone elses canonical log" was renamed and mislabelled `child_failed` although no child was spawned).
