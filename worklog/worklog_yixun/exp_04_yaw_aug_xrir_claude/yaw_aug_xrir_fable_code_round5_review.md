## Findings

### Should-fix

**1. `tools/results_table.py:136-152` — an edited generated block is salvaged verbatim into `## Manual`, so a hand-edited number survives regeneration (as a stale second table).**
`_preserve_manual` recomputes the block's stamp; on mismatch it moves the *entire* old block (minus the stamp and markers) under `## Manual`. Verified: after replacing `1363.75 ± 15.8114` by `999.999 ± 0.001` inside the generated table and regenerating with `--force-md`, the generated block carries the JSON value (good), but the file now also contains, under `## Manual`, a second `# Model comparison` heading, the estimand paragraph and the full six-row table with `999.999 ± 0.001` — and this persists through every later regeneration (count stays 1, never removed). `be5830d`'s own test `test_manual_edit_inside_generated_block_survives` asserts exactly this behaviour. Plan §5 says "numbers never hand-edited"; the round-5 prompt asked to preserve "rows/notes that are **not produced by this tool**". A stale, unlabelled copy of the tool's table with a hand-edited cell is neither. *Fix (choose one, ~10 lines):* (a) fail closed — on stamp mismatch raise `ValueError('generated block was edited by hand; move your notes below the end marker and rerun')`, which is consistent with every other refusal in this pipeline; or (b) if salvage is wanted, wrap the salvaged text in an explicit marker (`<!-- salvaged from an edited generated block; these numbers are NOT canonical -->`), drop its `# Model comparison` heading and its table rows, and keep only prose. Update the test to the chosen policy.

**2. `tools/results_table.py:140` — a file with two generated blocks grows without bound.**
The salvage branch runs only when `count(BEGIN) == count(END) == 1`; otherwise the whole previous text (including the old stamped blocks) is treated as manual and a fresh block is prepended. Measured on a file where the generated block had been pasted twice: 15 023 → 22 551 → 30 079 → 37 607 bytes over three `--force-md` regenerations, BEGIN markers 2 → 5. The same happens if a manual note quotes the marker text. *Fix:* iterate over every `BEGIN…END` pair, drop each one whose stamp verifies, apply finding 1's policy to the rest; or refuse when more than one block is present.

**3. `tools/paired_compare.py:311-312, 362-363` — the augmented arm is admitted without its training provenance bound.**
A9 (plan §11) says the training launcher "is recorded, not compared — its identity reaches the analysis through the augmented checkpoint's sha256 **and the train completion bound as `mutable_inputs.train_completion`**". `admit_run` validates the *names* in `mutable_inputs` (⊆ {control_args, train_manifest, train_completion, probe_receipt}) and binds whatever is present, but `mutable_inputs == {}` is accepted for an aug run. The eval launcher only binds what the operator passes on the command line (`tools/exp04_eval_launch.py:214-220`, `--bind-input name=path`), so an aug evaluation launched without `--bind-input train_manifest=… --bind-input train_completion=…` is admitted with no link to the attempt that produced the checkpoint. *Fix (3 lines):* in `admit_run`, `if arm['role'] == 'aug': require({'train_manifest', 'train_completion'} <= set(fields['mutable_inputs']), 'aug train provenance binding')`, plus a test; and the Planner's eval-launch command for the aug arm must pass both bindings (see "Fitness" below).
